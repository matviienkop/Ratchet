# Autonomous development systems compared with ai-dev

Research snapshot, 2026-11-20. The comparison uses upstream specifications, engineering accounts and the five pinned local source checkouts examined below. Runtime compatibility, recovery behavior on the self-hosted target, subscription usage and relative cost still require measurement.

## What exists in ai-dev

Chat registration, clone discovery, membership changes, revision-bound research, partial coverage, generated documents and local task import have working implementations. The PaNasMs registration exercise produced evidence for 17 of 18 declared sources. That exercised research workers. It did not exercise an autonomous change across two repositories. The scheduler, delivery loop, external task-provider adapters and token accounting are at the design stage. The internal provider owns a card file per task. Selecting Linear in project settings records a preference; writing to Linear still needs an adapter. ## Suggested workflow

1. **Receive and qualify.** Resolve the project from the chat or tracker event. Load the canonical card and acceptance criteria. Distinguish a question, a project-management request and a request to change code. Repeated delivery of the same event maps to the existing run.
2. **Plan and scope.** A research worker identifies affected repositories and the checks that cover their interaction. Persist the plan, relevant source revisions, blocking decisions and the owner’s approval where required. A project with 18 repositories might need just two for this change.
3. **Implement.** Assign an isolated working copy for each repository that will be edited. Give each worker its assignment, applicable rules and evidence links. Schedule independent changes concurrently and record dependencies between them.
4. **Verify and correct.** Run known checks directly. Give a reviewer the requirements, diff and exact tested revisions. Route a concrete failure to its owner with a short excerpt and a link to the log. A duplicate event does not spend another model call. Exhausted attempts leave a checkpoint and a question for the owner.
5. **Integrate and accept.** Run the cross-component check against the exact set of candidate revisions. Collect the per-repo PR/MR links where publication is authorized. One merged component leaves the overall task open until the other acceptance conditions are met. The owner receives a single summary in the originating chat.
6. **Recover at any step.** After restart, reconcile the canonical card, worktrees, existing PR/MRs, checks, and outstanding approvals. An old worker's late result cannot approve a newer revision.

## Decision experiment

Run the same scenarios on native Hermes Kanban and Archon, using disposable repositories, equivalent model settings and identical acceptance criteria. Begin with a single-repo fix. Then change a shared interface in two repos and run a consumer check against the candidate provider revision. Repeat a CI notification, cancel a task externally and restart the runner after the first review request was published. Verify that one task remains visible, exactly the intended changes and requests exist, the owner can resume in chat, and an unrelated project continues while the first waits.

Record accepted outcomes, human interventions, duplicate effects, model calls, input/output tokens including retries, and elapsed time. Record provider-reported usage where available and distinguish estimates. Compare cost per accepted change. Treat failure to preserve edits, permissions or approval state as a failed scenario. The result can support keeping Hermes, using a different executor behind the ai-dev adapter, or adopting a larger platform.
