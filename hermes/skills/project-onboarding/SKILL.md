# Manage a project from chat

For requests to change acceptance checks, edit the policy file that `ai-dev-card doctor` reports. Checks live under `repos` keyed by the repository path or origin URL: each has a `name`, an `argv` array, an optional `timeout` in seconds, `stage` (`pre_review` or `post_review`) and, for a registered project stand, `stand` with the stand name plus `project` on the repository entry. For example, a post-review integration suite is `{"name": "integration", "argv": ["make", "integration"], "stage": "post_review"}`. The owner can describe this in ordinary language. Change only what they asked for, run `ai-dev-card doctor` and confirm the result in the owner's language. When the policy file is under `/etc/ai-dev`, hand the change to the operator.

Include a brief stack and quality-tool inventory in the owner's onboarding
summary. Identify existing checks and propose additions for specific gaps.
Distinguish configured checks from checks actually run and report any unknown
coverage. Leave proposed tools for the owner's decision.

Include the scoped coding style and its source in the onboarding summary. For a new checkout, including a planned repository or an `empty` inventory entry, use the stack chosen in chat or identified from its scaffold. Save the baseline using `ai-dev-style-default PROJECT_DIR CHECKOUT --stack STACK` (add `--scope SUBDIR` for a component). For an unlisted stack, choose a widely adopted convention from the language or framework's maintained documentation and pass `--guide TEXT --source HTTPS_URL`. Honor explicit owner choices and existing framework settings first. When the stack or checkout is still undecided, defer selection until it is known. Report empty repositories separately from analyzed and unavailable ones.

For a request to add, remove or list repositories in an existing project, follow [repository changes](references/repositories.md). Use the registration steps below for new projects and onboarding resumes.

Accept the project name, free-form brief, repository or group links, and task tracker directly from the conversation. Answer in the owner's language. The owner can start with a sentence and supply more details in subsequent messages.

1. **Resolve the request.** Derive a stable project slug from its name and default to the internal Kanban. Preserve explicit choices and the original brief. For a new idea with no repositories, create an empty project. For an existing product, use the owner's source links or an exact identity already established for that project. If the source is still unknown, ask for one main repository or the GitHub organization / GitLab group containing the project. If the owner selects an external tracker and its destination is ambiguous, ask which team, project or space. Group missing details into one short question. Proceed directly when the answer is already in the conversation.
2. **Discover the repositories.** Use `ai-dev-discover --help` and pass the chat values as separate arguments. Use `--project SLUG`, `--name NAME`, `--description TEXT`, repeated `--source URL`, and `--primary URL` when the main repository is known. A group URL scopes discovery to the requested group. For a self-hosted GitLab subgroup, use `--kind gitlab-group` on the group source. A single repository URL identifies that repository. For a multi-repository product, follow explicit first-party component references in its public documentation within the requested scope; confirm genuinely ambiguous membership. Use `--tasks-provider` and `--tasks-scope-json` for a tracker override. For GitHub Projects, Linear or Jira, follow [tracker setup](references/trackers.md) to capture the destination and verify access. Keep repository origins credential-free. Use existing authorized access for private sources. If the service cannot see a source, ask which origin or scoped read connection to use. Keep tokens and passwords out of chat.
3. **Register or resume.** Allocate a temporary file owned by the service for `--output FILE`. Run `ai-dev project create --manifest FILE` with the configured workspace. The tools own this temporary handoff and the persistent project state. If resuming the same project, verify its saved origins match the owner's scope and call create with its existing `project.yaml`. A partial clone result (exit 1) still contains the project directory and each ready checkout. Start analysis on those checkouts immediately. Retry recoverable failures without duplicating completed ones. Report conflicting origins or path collisions. Use the returned absolute `project_dir`. Save an extended description supplied in chat as `docs/owner-brief.md` inside that project. Use a short summary in discovery and include the brief path in the owner report. Preserve prior owner edits on resume. Any inaccessible requested repositories remain outstanding.
4. **Delegate analysis.** Run `ai-dev-analyze PROJECT inventory`. For each `pending-analysis` checkout, delegate its absolute project path, checkout name, expected revision and the [research assignment](references/research.md). Group small related repositories within available concurrency, recording a separate result per checkout. Keep each worker's context scoped to its sources. Report missing delegation capabilities or blocked checkouts with the completed count.
5. **Finish registration.** Recheck inventory. Run `ai-dev-analyze PROJECT finalize` for full coverage, or `ai-dev-analyze PROJECT finalize --partial` when a requested checkout remains inaccessible. Partial finalization returns exit 2 and writes documents, inferred settings and candidate cards under `provisional/`. Use its report even on exit 2. Name each outstanding source, report the exact analyzed/declared count and ask for a scoped read connection when required. On resume, process missing revisions and run full finalization. Review the summary and scoped open questions. Report analyzed versus requested repositories, documentation and configuration paths, imported card counts, coverage gaps and remaining owner decisions. Keep private findings inside the project. External tracker settings are recorded locally. Publication, deployment and implementation start on separate requests.
